# Gateway humidity event classification (T09)

The PC gateway uses six recent humidity readings at the normal five-second cadence. It computes two features inspired by the moving averages in Lab 4. The first is the average of the last three readings minus the average of the first three. The second is the mean absolute change between neighboring samples. The model learns a center for each class from labeled windows and selects the nearest center after scaling the features using the training data.

| `aiEvent` | Training scenario |
| --- | --- |
| `stable` | Small variation around a baseline |
| `humidity_rising` | Sustained increase with measurement noise |
| `humidity_falling` | Sustained decrease with measurement noise |
| `humidity_fluctuating` | Larger alternating or irregular changes |

The model uses humidity in % RH so it can run on the humidity-only kit. Temperature, when present, is still forwarded as sensor telemetry. An isolated sample at high humidity can still belong to a stable window. CoreIOT RuleChain handles absolute humidity thresholds separately.

## Train and evaluate

From the repository root, run this command with Python. Training and inference use the standard library.

```powershell
python -m ai.train
```

The default dataset is generated by [train.py](train.py) with seed `261`. It contains 160 synthetic sessions with four six-reading windows per session. Levels, slopes and noise vary by session. The training code holds out 32 whole sessions (128 windows) and uses the other 128 sessions (512 windows) to fit the model and scales. [humidity_model.json](humidity_model.json) contains the fitted parameters. [evaluation.json](evaluation.json) records accuracy, class precision and recall, macro-F1, the confusion matrix and inference time measured on the training PC. The results describe the synthetic test set.

For a real-data evaluation, collect readings five seconds apart under known conditions, record independent sessions per class, then label each session from the observed scenario. Use one row per six-reading window in a CSV with `session,label,rh1,rh2,rh3,rh4,rh5,rh6` as the header. Give all windows from a recording the same session ID. Use at least two independent sessions for each label so the training and test sets both contain that class.

```powershell
python -m ai.train --dataset path/to/labeled-humidity.csv --output-dir build/ai-real
```

## Run the model on the gateway

Keep the local MQTT broker running. In two PowerShell windows from the repo root, start the synthetic classroom and the bridge using the corresponding sandbox configuration.

```powershell
python gateway/simulator.py --minimal --device-id classroom-01-sim --random
```

```powershell
python -m gateway.bridge --env-file gateway/.env --ai-model ai/humidity_model.json
```

The first prediction follows the sixth accepted reading. Samples less than 2.5 seconds apart are skipped by the model, and a missing humidity reading or a gap over 15 seconds starts a new window. Gateway telemetry still follows the regular MQTT path. The bridge includes `aiEvent` and `aiModel` in the same `v1/devices/me/telemetry` record as the reading. Check both keys in **Latest telemetry** for `classroom-01-sim`. The existing **Gateway AI events** table uses `aiEvent` if its alias points to that device. For a stable demo, run the simulator with `--humidity 65` instead of `--random`.

To verify locally, the [gateway MQTT tests](../tests/gateway/test_gateway.py) send a rising humidity scenario through the bridge and check the resulting `aiEvent` on the simulated cloud broker. Save separate evidence for a signed-in CoreIOT run and for evaluation with real sensor data.
