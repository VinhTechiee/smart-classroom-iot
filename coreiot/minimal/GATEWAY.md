# T15 · CoreIOT Gateway compatibility proposal

The current design uses one cloud MQTT Device API connection and access token per classroom entity. ThingsBoard's Gateway API multiplexes downstream devices over one authenticated MQTT connection. The public CoreIOT `4.2.0PE` API includes `GET /api/device-connectivity/gateway-launch/{deviceId}/docker-compose/download` for the official gateway service. Confirm the **Is gateway** device option and exercise its `v1/gateway/*` topics in the signed-in course tenant. [CoreIOT OpenAPI](https://app.coreiot.io/v3/api-docs) · [ThingsBoard Gateway API](https://thingsboard.io/docs/reference/gateway-api/overview/) · [Gateway device settings](https://thingsboard.io/docs/user-guide/devices/#gateway-devices)

T15 is an optional lab exercise. It needs tenant Gateway capability, a reachable approved MQTT endpoint and a Member B adapter for the multiplexed topics. The available fallback is the repository's synthetic `python -m coreiot.simulator` on the existing per-device MQTT route. The upstream Gateway topics cover telemetry, attributes and RPC. Gateway-mediated firmware transfer would still require a separate A/B contract and test. [OTA handoff](../platform/OTA.md)

## Sandbox design

1. Create `classroom-gateway-lab` with **Is gateway** enabled and a dedicated gateway access token. Verify the permitted MQTT endpoint and TLS availability. Port `8883` was unreachable from the current network, so the lab cannot assume TLS reachability. Leave **Overwrite activity time** off in the lab so child activity can reflect their own messages. Check child telemetry timestamps separately from activity state.
2. Use disposable downstream entities, for example `classroom-gw-test-01` and `classroom-gw-test-02`. Pair each local ID with its exact cloud entity name in an explicit mapping. Provision those names in the intended profile before connecting. On compatible ThingsBoard instances an unknown connect name may create an entity or, if supplied, a profile, so only forward mapped identities. Confirm each downstream UUID in the tenant and validate the dashboard or temporary aliases against those UUIDs. [Connect and disconnect](https://thingsboard.io/docs/reference/gateway-api/overview/#device-connect)
3. Subscribe to `v1/gateway/rpc`, `v1/gateway/attributes` and `v1/gateway/attributes/response` on the gateway session. On each reconnect, register online downstream devices again. Publish `{"device":"classroom-gw-test-01"}` to `v1/gateway/connect` at QoS 1 and wait for PUBACK before sending its data. Use the same mapping on `v1/gateway/disconnect` when that device goes offline. [Topics and gateway credentials](https://thingsboard.io/docs/reference/gateway-api/overview/)

| Operation | Current cloud connection | Gateway lab connection |
| --- | --- | --- |
| Authentication and identity | Classroom access token selects its device | Gateway token authenticates the session and the downstream name selects the device |
| Telemetry | `v1/devices/me/telemetry` with `{"ts":1700000000000,"values":{...}}` | `v1/gateway/telemetry` with `{"classroom-gw-test-01":[{"ts":1700000000000,"values":{...}}]}` |
| Attributes | `v1/devices/me/attributes` and per-device request/response topics | Publish client attributes by downstream name on `v1/gateway/attributes`. Request `{"id":1,"device":"classroom-gw-test-01","client":false,"keys":["labSetting"]}` on `v1/gateway/attributes/request` and match its response. Shared pushes carry `device` plus `data` on `v1/gateway/attributes`. |
| Two-way `setLamp` | Request ID in `v1/devices/me/rpc/request/{id}`, reply to `v1/devices/me/rpc/response/{id}` | Receive `{"device":"classroom-gw-test-01","data":{"id":7,"method":"setLamp","params":true}}` on `v1/gateway/rpc`. Return `{"device":"classroom-gw-test-01","id":7,"data":{...}}` on the same topic with the matched application ACK as `data`. |

Use the existing local command and ACK topics and schema. Maintain pending requests keyed by gateway session, child identity, and cloud request ID, and correlate the local ACK by child and local command ID. Reuse the current gateway timeout and cache behavior in any approved implementation. The RuleChain reads its policy from server attributes. Synchronize only the shared or client keys agreed with Member B. If B's gateway publishes AI events on its own device entity through the Device API, add an alias for that entity, use it in the AI widget and include classroom identity in B's agreed event format. [Gateway telemetry](https://thingsboard.io/docs/reference/gateway-api/telemetry/) · [Gateway attributes](https://thingsboard.io/docs/reference/gateway-api/attributes/) · [Gateway RPC](https://thingsboard.io/docs/reference/gateway-api/rpc/)

## Independent acceptance

- Record the course tenant version, gateway entity ID, both downstream IDs and proof of one session. Verify that each child receives its own timestamped telemetry and that the mapping creates zero unexpected entities.
- Verify a client attribute uplink, a shared-attribute response and a server-pushed shared update on one child. Check that the other child remains untouched.
- Send both `setLamp` states to one child. Match the two-way response and fresh `lamp` telemetry to the target. Exercise a local ACK timeout and a reconnect while the other child continues reporting. Verify that an expired command does not replay.
- Preserve the existing per-device MQTT route for the classroom deployment. Member B owns an eventual lab adapter and any production change after this test. The API proposal and documentation review are complete. Course-tenant Gateway support and the optional T15 demonstration remain pending.
